## Embedding 데이터 시각화

Embedding된 텍스트 데이터 분포를 살펴보기 위해 UMAP을 활용한 차원축소 기법을 활용하여 데이터를 시각화 하였다.

### 왜 UMAP을 사용했는지?

**UMAP을 활용하면 텍스트 데이터의 의미적 유사성을 반영한 자연스러운 클러스터링 경향과 데이터 분포를 더 명확하게 시각화할 수 있기 때문이다.**

텍스트 데이터는 고차원 공간에 존재하며, 그 구조가 매우 복잡하고 비선형적인 특징을 갖는다. 예를 들어, 의미적으로 유사한 문장이나 단어들이 비슷한 위치에 군집을 이루지만, 이들 사이의 관계는 단순한 직선이나 평면으로 표현하기 어렵다.

텍스트 임베딩은 단어 간, 문장 간 의미적 관계를 반영하기 위해 복잡한 비선형 패턴을 내포하는데, PCA와 같은 선형 차원 축소 기법은 데이터의 분산을 최대한 보족하는 데는 효과적이지만, 이 과정에서 데이터 내에 숨겨진 비선형 구조나 국소적 특성을 잘 포착하지 못한다.

반면, UMAP은 데이터의 국소적 이웃 관계를 보존하면서 저차원 공간에 임베딩하는 비선형 차원 축소 기법으로 복잡한 데이터 구조를 효과적으로 표현한다.

## Embedding값을 통한 클러스터링

임베딩 값을 `cosine-similarity`로 값을 변환하여 데이터 클러스터링을 진행하고자 하였으나 다음과 같은 한계에 부딪혔다.

## Embedding값을 통한 클러스터링의 한계

1. `cosine-similarity`값을 통해 데이터 클러스터링을 하는 알고리즘인 Spectral Algorithm을 이용하고자 하였으나, 데이터의 크기가 (3121, 3121)으로 나타났고 이 데이터를 통해 최적의 클러스터링 k값을 찾기 위해서는 **많은 시간을 투자해야했다.**
2. UMAP으로 2차원/3차원으로 데이터를 축소하여 경계면이 뚜렷한가를 살펴보았지만 클러스터의 양상이 비교적 뚜렷하지 않을 뿐 더러, 텍스트라는 고차원이고 의미를 가장 중요시하게 보아야 하는 데이터를 축소하여 확인해본 결과, **거리보존률이 0.3 미만에 그쳐 의미를 다 잃어리는 문제가 발생**해 클러스터링을 진행하는 것에 많은 애로가 있었다.
3. 결국 시간을 다소 소비하더라도, 원본 데이터를 클러스터링을 시도하였으나 (최대한의 시간을 절약하기 위해 군집 개수인 k가 1500 미만까지만 계산하였다.), **차원의 저주**로 인해, “클러스터의 경계가 뚜렷한가?” 의 평가지표로 삼는 실루엣 점수와 데이비스 볼딘 점수가 매우 비효율적인 점수의 양상을 띄었다.
    1. 실루엣 점수는 0.1 이상으로 올라가는 구간이 k가 1,000개 이상일 때 처음 올라갔다.
    2. 데이비스 볼딘 점수는 k가 어떤 값이든 상관없이 1에서 내려가는 평가 지수를 찾아볼 수 없었다.

문제를 해결하기 위해 다음과 같은 아이디어를 통해 다음 작업을 진행했다.


### 문제 해결을 위한 대안 마련

문제를 정리하자면 다음과 같다.

1. 문장 유사도 기반을 통한 텍스트 클러스터링 결과가 만족스럽지 않고, 구분하였다 한 들, 그 경계가 명확하지 않음.
2. 다른 클러스터링 방식인 k-NN 알고리즘을 사용해보았지만, k의 명확한 개수가 나오지 않고 어느 한 점을 찍고 사용해야하는 k-NN 알고리즘은 추천 방식으로 자주 작동되기 때문에 클러스터링으로써 사용하기에는 다소 부적절.

### 연관분석의 근간

각 질문에서 핵심 키워드를 3개씩 추출하고, 이를 모아 하나의 키워드 집합을 구성하였다. 이 과정에서 서로 다른 질문에서 동일한 키워드가 반복적으로 등장하게 되며, 이는 곧 **키워드 간 *공출현 관계를 형성**한다. 이러한 구조적 특성을 정량적으로 파악하고, 키워드 간 의미 연결성을 더 명확히 드러내기 위해 연관분석을 적용하였다.

**공출현이란? : 말 그대로 같이 등장하는 것.*

## 연관 분석을 위한 데이터 전처리

```python
encoder = TransactionEncoder()
encoder_T = encoder.fit_transform(question_series)
encoder_matrix = pd.DataFrame(encoder_T, columns= encoder.columns_) * 1
display(encoder_matrix)
```

연관분석을 위해 질문별 키워드 리스트를 **이진 행렬(binary matrix)**로 변환하였다. 이를 위해 TransactionEncoder를 활용하여 각 질문이 특정 키워드를 포함하는지 여부를 0과 1로 표현하였고, 그 결과 연관 규칙 탐색에 바로 적용할 수 있는 데이터 구조를 구축하였다. 이 과정을 통해 단어 간 공출현 관계를 정량적으로 분석할 수 있는 기반을 마련하였다.

<img src="https://saeran-iren12.notion.site/image/attachment%3Ab1432a38-3301-4fb4-bdb3-cb6062320814%3Aimage.png?table=block&id=26ae008e-cc3a-80ab-b918-d90dbdee1440&spaceId=941bde33-6d61-4dec-a0a5-5165a3ad9646&width=1420&userId=&cache=v2">

```python
frequent_itemsets = apriori(encoder_matrix, min_support=0.001, use_colnames=True)
rules = association_rules(frequent_itemsets, metric="lift", min_threshold=1.0)
```

`apriori`를 통해 빈발 항목 집합을 찾고 `association_rules`를 통해 연관 규칙을 생성하였다.

- `apriori()` : 자주 함께 등장하는 항목 집합 찾기
    - `min_support=0.001` : 전체 데이터 중 0.1% 이상 등장하는 항목 집합만 추출한다.
        
        → 너무 희귀한 조합은 제외하고, 의미 있는 패턴만 남기기 위한 설정
        
    - `use_colmnaes=True` : 인덱스가 아닌 실제 단어 이름으로 결과를 보여준다.
- `association_rules()` : 연관 규칙 생성
    - `metric=”lift”` : Lift를 기준으로 연관 규칙을 추출한다.
    - `min_thjresholed=1.0` : Lift가 1보다 큰, 즉 우연 이상의 상관관계가 있는 항목들만 필터링한다.

---

`Support`, `Confidence`, `Lift` 정의는 다음과 같다.

- `Support (지지도)` : 전체 내역 중 A와 B가 동시에 포함된 비율
- `Confidence (신뢰도)` : A가 등장했을 때, B가 추가로 등장할 확률
- `Lift (향상도)` : A가 등장했을 때, B가 추가로 등장할 가능성에 관한 지표

```python
G = nx.Graph()

# 연관 규칙을 노드-엣지로 변환
for _, row in rules.iterrows():
    for antecedent in row['antecedents']:
        for consequent in row['consequents']:
            if G.has_edge(antecedent, consequent):
                G[antecedent][consequent]['weight'] += row['lift']
            else:
                G.add_edge(antecedent, consequent, weight=row['lift'])
```

여기서 `Lift`값을 가중치를 두어 의미연결망을 구성하고자 하였는데, 이유는 다음과 같다.

## **Q. 왜 Lift값을 가중치를 두었는가?**

`Support`와 `Confidence`는 항목 간의 동시 발생 빈도나 조건부 확률에 기반한 지표로, **빈도 중심의 관계성**을 보여주는 데 그친다. 예를 들어 A와 B가 자주 함께 등장한다는 것은 유의미해 보이지만, 각각이 워낙 자주 등장하는 항목이라면 단순 동시 빈도는 우연한 공존일 가능성도 있다.

반면, `Lift`는 두 항목의 동시 발생이 우연이 아닌지를 측정하는 지표로, A와 B가 독립일 때 기대되는 발생 확률 대비 실제 발생 확률의 비율을 나타낸다.

즉, `Lift` 값이 1보다 크면 A와 B는 **우연 이상의 상관관계**를 가진다고 볼 수 있고, 이는 의미망 분석에서 단어 간의 실제적 연관성을 가늠하는 데 더 적합하다고 판단하였다.

따라서, 단순히 많이 등장했다고 해서 의미가 연결된다고 판단하기보다는, `Lift`를 통해 실질적 의미 연관성을 기반으로 텍스트 카테고리들 간의 네트워크를 구성하고자 하였다.

### **Q2. Louvain 알고리즘 이란?**

네트워크(그래프)에서 의미 있는 그룹(커뮤니티)을 찾기 위한 군집 알고리즘이다.

> 핵심 아이디어
> 그래프에서 서로 밀접하게 연결된 노드 집단(커뮤니티)을 찾는다.
> 
> 이때 사용되는 지표가 Modularity (모듈성):
> 
> - "내부 연결은 조밀하고, 외부 연결은 드문" 구조일수록 모듈성이 높다.

작동 방식 요약:

1. 각 노드를 하나의 커뮤니티로 시작.
2. 각 노드를 옮겨가며 모듈성(Modularity)을 가장 크게 높이는 방향으로 이동.
3. 커뮤니티를 재구성하고, 노드들을 압축해서 새로운 그래프 구성.
4. 이 과정을 모듈성 변화가 더 이상 없을 때까지 반복.

# 💡프로젝트 내 회고

## 만족스럽지만 만족스럽지 않은 클러스터링

이번 분석에서 가장 큰 도전 과제는 **질문 데이터를 수치나 벡터로 단순 표현하기 어려웠다는 점이었다.** 전통적인 클러스터링 알고리즘만으로는 텍스트의 의미를 충분히 반영하기 힘들었기에, 이를 보완하기 위해 Gemini Pro 2.5라는 (2025년 6월 30일 기준) 최신 모델과 이를 통한 연관 분석 및 네트워크 군집 알고리즘을 적용하여 “인간의 추론 영역”에 근접한 텍스트 분류 작업을 했던 것은 인상적이었다.

또한, 특정 카테고리의 질문 경험이 리텐션에 영향을 줄 수 있다는 가설은 직관적으로 쉽게 연결되지 않았지만, 이를 자연어 처리 기법으로 검증하려 했던 시도는 창의적이라는 평가를 받을 수 있었다. 이러한 점에서 분석 접근 자체는 의미 있는 도전이었다고 본다.

그러나 아쉬움도 남았다. **Vertex AI를 활용한 질문 카테고리 분석이 상/하위 집단 간 선호도를 보조적으로 보여주는 데 그쳤다는 점이다.** 코호트 리텐션 그룹을 메인으로 두다 보니 어쩔 수 없는 선택이었지만, 만약 카테고리별 결과를 더 풍부한 시각화로 보완했다면, 클러스터링의 활용도가 더욱 높아졌을 것이다.

결과적으로 이번 시도는 “잘 작동했지만, 충분히 다듬지 못한” 클러스터링이었다고 정리할 수 있다. 만족스러운 성과와 동시에, 후속 분석에서 개선할 여지를 분명히 남긴 경험이었다.

## 결국 데이터 분석의 핵심 스킬은 “하드스킬”이 아닌 “소프트스킬”

이번 프로젝트를 돌아보면, 내가 부족했던 점은 하드스킬에 몰입한 나머지 소프트스킬, 특히 커뮤니케이션을 충분히 챙기지 못했다는 점이었다. 프로젝트의 핵심 주제였던 “리텐션 증진을 위한 A/B 테스트와 가이드라인 설계”와 “핵심 KPI는 친구 수”라는 목표를 고려할 때, 팀원들이 나와 다른 영역에서 논의하더라도 **결국 내가 전체 맥락을 이해하고 있어야 한다는 사실**을 뼈저리게 느꼈다.

팀원들이 A에 대해 논의할 때 적극적으로 참여하며 다양한 대책을 고민했지만, 내가 실제로 집중하고 있었던 일은 B였다. 결과적으로 **B에 대한 기술적 몰입을 조금 내려놓고, A에 대한 탐구와 팀 논의에 더 보조적인 역할을 했더라면** 프로젝트 진행과 팀 성과에 더 기여할 수 있었겠다는 아쉬움이 남는다.

## 그래도 기술적 성과는 얻었다

학교를 졸업하기 전, GCP를 이용한 실습과정을 교육받았지만, 실제 프로젝트에서는 제대로 활용하지 못한 부분이 많아 아쉬움이 남아 있었다. 이번 프로젝트를 통해 분석 환경을 클라우드 기반으로 구축하고, 대용량 데이터를 BigQuery로 처리하는 경험을 쌓으면서 GCP에 대한 이해와 기술적 성취를 크게 향상시킬 수 있었다.

특히 Cloud SQL과 BigQuery를 비교하며 이해한 점이 매우 유익했다. 두 서비스 모두 데이터베이스를 다루지만 성격과 목적이 다르다. **Cloud SQL**은 MySQL, PostgreSQL 등 관계형 데이터베이스를 클라우드에서 관리할 수 있는 서비스로, **트랜잭션 처리와 실시간 데이터 운영**에 적합하다. 반면, **BigQuery**는 대규모 분석용 데이터 웨어하우스로, **수십억 건 이상의 데이터를 빠르게 집계·분석할 수 있는 환경을 제공**한다. 프로젝트에서는 이러한 특성을 고려해, 운영 데이터는 Cloud SQL에 저장하고, 분석용 집계 데이터와 대규모 로그 데이터는 BigQuery에서 처리함으로써 효율적인 데이터 관리와 분석 환경을 구성할 수 있었다.
